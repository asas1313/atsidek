# ADR-0002: Entitlements data model, beta feature flag, and the first premium feature's schema

Status: **Accepted** — confirmed by the user (see
`docs/specs/taupymo-tikslai/taupymo-tikslai-atskyrimas.plan.md` §4). Scope expanded by
the user beyond the original entitlements-foundation-only draft to include the first
real premium feature (`SAVINGS_TRACKING`) end-to-end; this revision reflects that, plus
five further binding fixes the user made on final approval: `TIMESTAMPTZ` everywhere
(not `TIMESTAMP`), `Clock.systemUTC()` as the default clock, DB `CHECK` constraints on
`savings_goal`/`savings_contribution` amounts and on month-alignment, transactional
contribution cleanup on goal replacement, and the plan's new session-resilience task for
a deleted `app_user` row. See the plan's §5/§6/§7 for the full reasoning; only the schema
and clock decisions are restated here since they live in this ADR's scope.

## Context

`docs/specs/taupymo-tikslai/PLAN-atskyrimas.md` stage 4 ("Teisių sluoksnis") requires an
`entitlement(user_id, feature, source, valid_from, valid_until)` table, a single
Java-side check point, and a beta-mode feature flag toggleable without a deploy.
`docs/specs/monetizacija/PLAN.md` independently drafts the same `entitlement` shape and a
generic `app_setting` table for its own, later `paywall_enabled` flag. The user then
expanded this increment's scope to also ship the first real premium feature
(`SAVINGS_TRACKING`: one saved goal + manual progress marking), and added hard,
project-wide security requirements (`docs/specs/saugumas/PLAN.md` informed several of
these) that materially change this ADR's data model from its original draft.

## Decision

### Identity reference (confirmed, see ADR-0001)

Every table below references `app_user(id)`, an internal **UUID** — not email, not the
bank module's `"google:" + sub` string.

### Standing rule: `ON DELETE CASCADE` on every foreign key into `app_user`

**This is a hard rule for this increment's tables and for every future table that holds
per-user data in this codebase, not a one-off choice for `entitlement`/`savings_goal`/
`savings_contribution`.** Any later table (including whatever `monetizacija` eventually
adds — `subscription`, `payment`, `ai_usage_event`, etc., and anything
`docs/specs/saugumas/PLAN.md`'s own work adds) that references `app_user`, directly or
transitively through another per-user table, must do so with `ON DELETE CASCADE`. This
makes account deletion (GDPR) structurally complete by construction — deleting one
`app_user` row is sufficient to remove everything, with no per-table deletion code to
remember or forget.

### Schema (Flyway `V5`–`V9`, confirmed)

All timestamp columns are `TIMESTAMPTZ` (confirmed correction — not `TIMESTAMP`); `DATE`
is kept only for `target_date`/`month`, which are calendar business dates, not instants.

```sql
-- V5
CREATE TABLE app_user (
    id UUID PRIMARY KEY,
    auth_provider VARCHAR(20) NOT NULL,
    provider_subject VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (auth_provider, provider_subject)
);

-- V6
CREATE TABLE app_setting (
    setting_key VARCHAR(60) PRIMARY KEY,
    setting_value VARCHAR(200) NOT NULL
);
-- No seed row for goals_beta_mode_enabled: absence = OFF (confirmed default).

-- V7
CREATE TABLE entitlement (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    feature VARCHAR(40) NOT NULL,
    source VARCHAR(20) NOT NULL,            -- 'BETA' today; 'PAYMENT' reserved for monetizacija
    valid_from TIMESTAMPTZ NOT NULL,
    valid_until TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ix_entitlement_user_feature ON entitlement (user_id, feature);

-- V8
CREATE TABLE savings_goal (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    goal_type VARCHAR(30) NOT NULL,
    amount NUMERIC(14,2) NOT NULL CHECK (amount > 0),
    target_date DATE,
    assumptions JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (user_id)                         -- "exactly one goal per user", enforced in the DB
);

-- V9
CREATE TABLE savings_contribution (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    goal_id UUID NOT NULL REFERENCES savings_goal(id) ON DELETE CASCADE,
    month DATE NOT NULL CHECK (month = date_trunc('month', month)::date),
    amount NUMERIC(14,2) NOT NULL CHECK (amount >= 0),
    UNIQUE (goal_id, month)
);
```

Application code additionally mirrors `/api/v1/compare`'s existing manual amount check
(`eu.atsidek.web.TaxApiController.checkAmount`, `MAX_AMOUNT = 100000000`) for both
`amount` columns — the DB `CHECK`s above are a backstop against a bug bypassing that
layer, not the primary validation surface (they don't produce a friendly 400 message).

`savings_contribution` cascades transitively: deleting `app_user` cascades to
`savings_goal`, which cascades to `savings_contribution` — no direct FK to `app_user` is
needed on the contribution table.

### Check point (confirmed)

`eu.atsidek.entitlement.EntitlementService.hasFeature(UUID appUserId, Feature feature)`
is the single Java-side check point. It uses an **injectable `java.time.Clock`, default
`Clock.systemUTC()`** (confirmed correction — not `systemDefaultZone()`; `Europe/Vilnius`
is a display-only concern, applied in Thymeleaf templates, never in storage or
comparisons) for both:
- comparing `valid_from`/`valid_until` on real `entitlement` rows, and
- the beta-flag's short-TTL (~30s) in-memory cache in front of an `app_setting` read.

No test for this logic uses `Thread.sleep` or waits on the wall clock; a mutable test
`Clock` is advanced explicitly instead. When `goals_beta_mode_enabled` is `true`, any
authenticated user has every `Feature`; when `false`, real `entitlement` rows (currently
always empty, since nothing issues one yet — `SAVINGS_TRACKING` grants only come from the
global beta flag in this increment) govern.

### `SAVINGS_TRACKING`'s own data access pattern (new in this revision)

- Every repository query for `savings_goal`/`savings_contribution` is scoped
  `WHERE user_id = :currentUser` (or via a join to a goal already scoped that way) **in
  the SQL itself** — never "fetch by id, then check the owner in Java". This is the same
  principle `docs/specs/saugumas/PLAN.md` states for all future per-user data access, and
  is treated here as a structural guard against ever adding a code path that skips it.
- Any request for another user's goal `id` returns **`404`**, identical to a
  non-existent id — never `403`, which would leak that the id exists. A missing
  `SAVINGS_TRACKING` entitlement on the *collection* endpoint (creating a goal) returns
  `403` instead, since the feature's existence is not itself a secret.
- A dedicated IDOR test exercises this with two distinct real logged-in users, one
  requesting the other's goal id.
- **Replacing an existing goal requires explicit confirmation and deletes its
  `savings_contribution` rows in the same transaction (confirmed correction).** Because
  "exactly one goal" is implemented as an upsert that keeps the same `goal.id` (see
  Alternatives below), a plain `UPDATE` would otherwise leave old contribution rows
  attached to the reused id, silently mixing an old goal's recorded months into a new
  goal's progress calculation — `ON DELETE CASCADE` does not help here since the goal row
  itself isn't being deleted. `SavingsGoalService.save(...)` therefore never replaces
  silently: a first save for a user with no existing goal proceeds unconditionally; a
  replacement only proceeds once the caller passes an explicit `confirmed=true`, at which
  point the contribution delete and the goal update happen inside one `@Transactional`
  method.
- **No pricing policy is encoded here.** Per the user's explicit instruction, whether
  `SAVINGS_TRACKING` stays free for all logged-in users or becomes paywalled later is
  deferred to a future decision based on beta usage data; this schema and
  `EntitlementService` only implement "beta flag on + logged in ⇒ granted", nothing more.

### Flag administration and Python integration (unchanged from the original draft)

- No admin UI ships yet; the flag is flipped with a documented manual SQL statement
  (plan §6 task 14 / `DEPLOY.md`).
- No Python-facing entitlements endpoint is added; nothing in Python consumes
  entitlements until a premium AI feature (`AI_PLAN_CHAT`) exists.

## Consequences

- `Feature` stays a closed Java enum; adding a premium feature later is one enum value,
  not a schema change.
- Because `SAVINGS_TRACKING` is now real (not just a placeholder matrix entry), this ADR
  now also governs the `savings_goal`/`savings_contribution` shape, not only
  `entitlement`/`app_setting` — scope intentionally widened from the original draft.
- "Exactly one goal, enforced by `UNIQUE(user_id)`, with upsert-on-save instead of a
  delete endpoint" means there is currently no way to reset/clear a goal short of
  replacing it with a new calculation or deleting the whole account; acceptable for this
  increment's single-goal scope, revisited if/when multi-goal ships.

## Alternatives considered

- Env-var-only beta flag: rejected — cannot be toggled without a restart, and the spec
  explicitly requires "without a deploy".
- Per-feature boolean columns on `app_user` instead of a row-per-grant `entitlement`
  table: rejected — cannot represent time-bounded, source-tagged grants needed once real
  payments exist.
- A separate delete-goal endpoint instead of upsert-on-save: rejected for this increment
  as unnecessary extra surface given the "exactly one goal" constraint; nothing prevents
  adding one later.
- Letting the application layer be the only enforcer of "one goal per user" (no DB
  constraint): rejected — `UNIQUE(user_id)` costs nothing and removes a whole class of
  race-condition bugs.
