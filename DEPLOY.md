# Diegimas į Hetzner

Architektūra: vienas VPS, `docker compose` paleidžia `app` (Spring Boot) ir `caddy` (HTTPS su automatiniais Let's Encrypt sertifikatais).

## Duomenų bazė: PostgreSQL + Flyway (nuo F0 fazės)

Nuo F0 fazės aplikacija naudoja **tikrą PostgreSQL** (anksčiau – H2 failas su `MODE=PostgreSQL`
dialektu). Schema valdoma **Flyway** migracijomis (`src/main/resources/db/migration/`), ne
`schema.sql`/`spring.sql.init.mode`:
- `V1__init.sql` – esamos 5 lentelės (`bank_account`, `statement_import`, `bank_transaction`,
  `classification_rule`, `user_setting`), perkeltos iš buvusio `schema.sql` be sintaksės pakeitimų
  (`GENERATED BY DEFAULT AS IDENTITY` standartiškai palaikoma PostgreSQL 10+).
- `V2__migrate_psd_settings.sql` – buvusi vienkartinė duomenų migracija (`psd_from`/`psd_to` →
  `psd_from_2026`/`psd_to_2026`), atskirta nuo DDL į savo migraciją.

Flyway paleidžiamas automatiškai paleidus aplikaciją (Spring Boot numatytieji nustatymai, jokio
papildomo `spring.flyway.*` konfiguravimo nereikėjo).

### Prisijungimo duomenys (env, NIEKADA repo)

`SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD` – privalomi
staging/production aplinkų `.env` failuose (`/opt/atsidek/<aplinka>.env`, žr. žemiau). Staging ir
production PostgreSQL jau veikia **atskirame LXC serveryje** `192.168.68.106:5432` (duomenų bazės
`atsidek_staging` / `atsidek_prod`, atskiri vartotojai, prieiga leidžiama tik iš konteinerių
išeinančio IP `192.168.68.104`). Pavyzdys `/opt/atsidek/staging.env` papildymui:

```bash
SPRING_DATASOURCE_URL=jdbc:postgresql://192.168.68.106:5432/atsidek_staging
SPRING_DATASOURCE_USERNAME=atsidek_staging
SPRING_DATASOURCE_PASSWORD=<slaptažodis iš slaptažodžių tvarkyklės>
```

### Lokalus dev su Docker Compose

`docker-compose.yml` turi `postgres` servisą **TIK lokaliam dev**, su atskiru profiliu `local-db`
(sąmoningai, kad `deploy/deploy.sh` – kuris visada naudoja `--profile tunnel` – jo NIEKADA
neužvestų staging/production serveryje):

```bash
docker compose --profile local-db up -d --build
```

Tai paleidžia `app` + `assistant` + lokalų `postgres` (duomenys tvarioje `postgres_data` talpoje).
`SPRING_DATASOURCE_*` numatytosios reikšmės `docker-compose.yml` nukreiptos į šį lokalų servisą –
jų keisti nereikia. Be `--profile local-db` lokalus Postgres servisas NEPASILEIS (taip pat
`--profile caddy`/`--profile tunnel` naudojimas kituose variantuose jo savaime neužveda).

Be Docker Compose (pvz. IDE paleidimui): `src/main/resources/application.yml` numatytoji reikšmė –
`jdbc:postgresql://localhost:5432/atsidek` (vartotojas/slaptažodis `atsidek`/`atsidek`) – paleisk
bet kokį lokalų Postgres su tokiais duomenimis, arba override'ink per env/`.env`.

### Testai (Testcontainers)

`mvn test` integraciniai testai (`@SpringBootTest` klasės) naudoja **Testcontainers** su realiu
PostgreSQL konteineriu per Spring Boot `@ServiceConnection` (žr.
`src/test/java/eu/atsidek/TestcontainersConfiguration.java`, importuojama į `AuthTest`,
`BankFlowTest`, `CalculatorControllerTest`, `TaxApiControllerTest`). Reikalauja veikiančio Docker
daemon'o. GitHub Actions `ubuntu-latest` runner'yje Docker yra iš anksto įdiegtas – papildomo
setup'o CI darbo eigoje (`.github/workflows/ci.yml`, `test` job'as) nereikėjo.

**Žinomas apribojimas (F0 PR)**: šio PR autoriaus (agento) sandbox'e NEBUVO Docker daemon'o
(`/var/run/docker.sock` neegzistuoja), tad `mvn test` lokaliai paleistas – 36 grynai vienetiniai
testai (TaxEngineTest, ClassifierTest, ParsersTest, CanonicalHostFilterTest, NoIndexFilterTest)
praėjo žali, o visi 27 testai keturiose `@SpringBootTest` klasėse (AuthTest, BankFlowTest,
CalculatorControllerTest, TaxApiControllerTest) baigėsi klaida **lygiai** „Could not find a valid
Docker environment“ – t. y. Testcontainers konfigūracija sukompiliuota ir bandė startuoti
konteinerį teisingai, bet sandbox'e nebuvo Docker, kad jį realiai paleistų. Nebuvo apsimesta, kad
šie testai praėjo – jie NEBUVO realiai patvirtinti žali. Žmogus (arba CI su Docker) turi paleisti
`mvn test` pilnai prieš merge, kad patvirtintų, jog visi esami testai lieka žali su Postgres.

### Duomenų perkėlimas: senas H2 failas → PostgreSQL

Vienkartinis įrankis `deploy/migrate-h2-to-postgres.sh` (+ `deploy/migrate-h2-to-postgres/Migrate.java`)
kopijuoja duomenis iš seno H2 failo į jau Flyway migracijomis paruoštą (tuščią) PostgreSQL DB.

**Naudojimas** (žmogus, su prieiga prie serverio/tinklo prie 192.168.68.106):

1. Sustabdyk aplikaciją tame aplinkos kataloge, kurio H2 failą perkeli (kad failas nebūtų
   naudojamas).
2. Paleisk aplikaciją bent kartą su nauju `SPRING_DATASOURCE_URL` (nukreiptu į naują/tuščią
   `atsidek_staging` ar `atsidek_prod` Postgres DB), kad Flyway sukurtų lenteles (V1, V2). Po to
   sustabdyk aplikaciją vėl (arba palik veikti – skriptas tik INSERT'ina, nekeičia schemos).
3. Padaryk `pg_dump` paskirties DB atsarginę kopiją (saugiklis, jei kažkas nepavyktų).
4. Vykdyk:
   ```bash
   deploy/migrate-h2-to-postgres.sh /opt/atsidek/<aplinka>-data/atsidek \
     "jdbc:postgresql://192.168.68.106:5432/atsidek_<aplinka>" atsidek_<aplinka> '<slaptažodis>'
   ```
5. Skriptas atsisako dirbti, jei paskirties lentelės NĖRA tuščios (saugiklis nuo pakartotinio
   vykdymo), parsisiunčia H2+PostgreSQL JDBC tvarkykles per Maven, kopijuoja 5 lenteles tiksliai
   nurodyta tvarka, atstato IDENTITY sekas (`setval`/`pg_get_serial_sequence`) ir pakartoja
   `psd_from`/`psd_to` → `psd_from_2026`/`psd_to_2026` perrašymą (V2 migracija jau įvykdyta ant
   tuščios DB prieš importą, todėl buvo no-op – šis žingsnis būtinas, kitaip senieji raktai liktų
   neperrašyti).
6. Paleisk aplikaciją su galutiniu `SPRING_DATASOURCE_URL` ir patikrink duomenis UI.

**SVARBU – šio PR agentas REALAUS vykdymo prieš staging/prod duomenis NEDARĖ** (nėra tinklo
prieigos prie `192.168.68.106`, ir tai negrįžtama operacija prieš dalinamą infrastruktūrą). Įrankis
buvo sukompiliuotas ir „dūminiu testu“ patikrintas prieš dvi laikinas H2 duomenų bazes (kopijavimo,
batch insert'o ir `psd` perrašymo logika veikia teisingai); PostgreSQL-specifinė sekos atstatymo
SQL (`setval(pg_get_serial_sequence(...))`) yra standartinis, plačiai dokumentuotas idiomas, bet
NEBUVO patikrinta prieš realų PostgreSQL (nebuvo Docker/tinklo). Realų vykdymą prieš
staging/production atlieka ŽMOGUS.

## 2. DNS (Cloudflare)

| Vardas | Tipas | Reikšmė |
| --- | --- | --- |
| `atsidek.eu` | A (ir AAAA) | serverio IP |
| `www.atsidek.eu` | A (ir AAAA) | serverio IP |

DNS valdomas Cloudflare. Abu įrašus nustatyk **DNS only** (pilkas debesėlis), kad Caddy pats gautų sertifikatus. Papildomi domenai (`atsidek.lt`, `kiekatideti.lt`) kol kas neužregistruoti; juos užregistravus, reikia pridėti jų DNS ir juos įrašyti į `Caddyfile` kaip nukreipimą į `atsidek.eu`.

Sertifikatai išduodami tik kai DNS jau rodo į serverį, todėl pirmiausia sutvarkyk DNS ir palauk (dažniausiai kelios minutės).

## Alternatyva: namų serveris (Proxmox) su Nginx Proxy Manager

NPM jau priima srautą kaip riaubyne.eu, todėl Caddy ir tunelio nereikia.

1. Proxmox: sukurk atskirą Debian/Ubuntu LXC (arba VM), 1 CPU, 1 GB RAM, 4 GB disko; LXC reikia *Nesting* (Options → Features). Duok jam pastovų LAN IP (DHCP rezervacija).
2. Įdiek Docker (3 skyrius), `git clone`, sukurk `.env`:

```bash
printf 'CONTROLLER_NAME="Andrius Riauba, IV pažyma Nr. 1440039"
CONTACT_EMAIL="info@atsidek.eu"
APP_BIND=0.0.0.0
' > .env
docker compose up -d --build
```

Be profilio paleidžiamas tik `app` (8080). Ugniasiene / Proxmox firewall leisk 8080 tik iš NPM LXC (100) IP.
3. NPM → Proxy Hosts → Add: domenai `atsidek.eu` ir `www.atsidek.eu`, scheme `http`, forward host = naujo LXC IP, port `8080`, įjunk *Block Common Exploits*. SSL skirtuke: Request a new certificate (Let's Encrypt), *Force SSL*, *HTTP/2*, *HSTS*.
4. Cloudflare DNS: `atsidek.eu` ir `www` nukreipk lygiai taip, kaip nukreiptas riaubyne.eu (tas pats viešas IP arba CNAME į jo hostname, ir tas pats Proxied / DNS only nustatymas).
5. `www` nukreipimą į pagrindinį domeną gali padaryti NPM (Redirection Host) arba palikti abu veikiančius.

## Alternatyva: namų serveris su Cloudflare Tunnel (be NPM)

Viešo IP ir atvirų prievadų nereikia, sertifikatus tvarko Cloudflare.

1. Proxmox: sukurk Debian/Ubuntu LXC (arba VM), 1 CPU, 512 MB–1 GB RAM, 4 GB disko. LXC reikia įjungti *Nesting* (Options → Features), kad veiktų Docker.
2. Įdiek Docker kaip 3 skyriuje, `git clone`, sukurk `.env` (CONTROLLER_NAME, CONTACT_EMAIL).
3. Cloudflare → Zero Trust → Networks → Tunnels → Create tunnel (Cloudflared) → nukopijuok **token**. Public hostname: `atsidek.eu` → HTTP → `app:8080`; antras: `www.atsidek.eu` → tas pats. (DNS įrašus sukuria pats Cloudflare; senus A įrašus tam hostname pašalink.)
4. Į `.env` pridėk `TUNNEL_TOKEN=...` ir paleisk:

```bash
docker compose --profile tunnel up -d --build
```

Caddy šiame variante nenaudojamas. `X-Forwarded-*` antraštes perduoda Cloudflare.

## Automatinis diegimas iš GitHub (staging + production)

Namų serveris (Proxmox LXC su Docker ir Cloudflare Tunnel). Workflow: `.github/workflows/ci.yml`.

Eiga: PR → `mvn test`. Merge į `main` → testai → **staging** (`staging.atsidek.eu`) automatiškai ir sustoja. **Production** (`atsidek.eu`) diegiamas tik rankiniu mygtuku: GitHub → Actions → „CI ir diegimas“ → **Run workflow** (šaka `main`). Jei to commit'o image jau sukurtas staging'e (`atsidek:<sha>`), production naudoja būtent jį. Diegia `deploy/deploy.sh`, kuris paleidžia `docker compose` ir tikrina, ar programa atsako.

### Vienkartinis paruošimas

1. **Runner**: tame pačiame LXC (kur Docker) įdiek GitHub self-hosted runner (repo → Settings → Actions → Runners → New self-hosted runner, Linux x64). Konfigūruodamas pridėk etiketę `atsidek`, įdiek kaip servisą (`sudo ./svc.sh install && sudo ./svc.sh start`), pridėk jo vartotoją į `docker` grupę. Runner jungiasi į GitHub pats, prievadų atidaryti nereikia.
2. **Aplinkų failai serveryje** (slaptų reikšmių GitHub'e laikyti nereikia):

```bash
sudo mkdir -p /opt/atsidek/production-data /opt/atsidek/staging-data
sudo tee /opt/atsidek/production.env >/dev/null <<'EOF'
CONTROLLER_NAME="Andrius Riauba, IV pažyma Nr. 1440039"
CONTACT_EMAIL="info@atsidek.eu"
TUNNEL_TOKEN=<esamo tunelio tokenas>
APP_PORT=8080
CANONICAL_HOST=atsidek.eu
NOINDEX=false
DATA_DIR=/opt/atsidek/production-data
EOF
sudo tee /opt/atsidek/staging.env >/dev/null <<'EOF'
CONTROLLER_NAME="Andrius Riauba, IV pažyma Nr. 1440039"
CONTACT_EMAIL="info@atsidek.eu"
TUNNEL_TOKEN=<naujo staging tunelio tokenas>
APP_PORT=8081
CANONICAL_HOST=staging.atsidek.eu
NOINDEX=true
DATA_DIR=/opt/atsidek/staging-data
EOF
sudo chown -R <runner-vartotojas> /opt/atsidek && sudo chmod 600 /opt/atsidek/*.env
```

3. **Staging tunelis**: Cloudflare Zero Trust → Tunnels → Create tunnel (antras) → Public hostname `staging.atsidek.eu` → HTTP → `app:8080`. Rekomenduojama papildomai uždėti Cloudflare Access (Zero Trust → Access → Applications), kad staging matytum tik tu.
4. **Esamas production**: dabartinį rankiniu būdu paleistą stack'ą sustabdyk (`docker compose --profile tunnel down` senoje direktorijoje), kad nesidubliuotų su `atsidek-production` projektu. Naujas projektas naudoja tą patį tunelio tokeną, todėl DNS keisti nereikia.
5. **GitHub Environments** (repo → Settings → Environments): sukurk `staging` ir `production`. Required reviewers privačiame repo veikia tik mokamuose planuose, todėl patvirtinimo funkciją atlieka rankinis „Run workflow“.

### Pastabos

- Self-hosted runner vykdo kodą tavo serveryje, todėl diegimo darbai paleidžiami tik `push` į `main`, o PR vykdo tik GitHub hostinamus testus. Jei repo viešas, Settings → Actions → General palik „Require approval for outside collaborators“.
- Atšaukimas: „Run workflow“ visada diegia `main` galvą, todėl atšaukimui padaryk `git revert` ir paleisk jį iš naujo.

## AI asistentas (atskiras servisas)

Konteineris `assistant` aptarnauja tik `POST /asistentas` (rezultato fragmentas); puslapį `/` su meniu rodo `app`. Reikia trijų dalykų:

1. `python ai/naujas_raktas.py` → raktą įrašyk į aplinkos `.env` kaip `ATSIDEK_API_KEY`, o maišą – kaip `API_KEY_HASHES` (be jos `/api/**` uždarytas ir asistentas gaus 401). Taip pat `ANTHROPIC_API_KEY`.
2. **Caddy** (variantas A): maršrutas jau yra `Caddyfile`.
3. **Cloudflare tunelis**: prie to paties hostname pridėk dar vieną Public hostname eilutę su **Path** `^/asistentas$` (anksčiau buvo `^/(asistentas)?$` – **pirma pakeisk taisyklę, tik tada diegk šią versiją**, kitaip `/` gaus 404 iš assistant) → `http://assistant:8000` ir pastatyk ją **virš** bendros eilutės (`app:8080`). **Nginx Proxy Manager**: Custom locations → tik `location = /asistentas { proxy_pass http://<IP>:8000; }` (Advanced skiltyje).

Patikra: `curl http://127.0.0.1:8000/healthz` (deploy.sh tai daro pats).
